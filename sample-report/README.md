# Sample report (moto mock account, not a real AWS account)

Everything in this folder was generated by running

    aws-security-audit demo --output-dir sample-report

The demo starts moto's in-process AWS mock with fake credentials, creates a
deliberately misconfigured account in it (`planted.txt` lists what), scans
`eu-west-2` and `us-east-1` with all 25 checks, applies one example
suppression, and writes the reports below. Account `123456789012` is moto's
default mock account ID. No real AWS account was scanned and no request left
the machine.

| File | What it is |
| --- | --- |
| `report.html` | Self-contained HTML report (open it in a browser) |
| `report.json` | Full JSON report, schema version 1 |
| `report.sarif` | SARIF 2.1.0 |
| `report.csv` | One row per finding |
| `console.txt` | The console table as printed by the CLI |
| `planted.txt` | The misconfigurations the demo creates before scanning |

Things to keep in mind when reading it:

- moto stamps IAM access keys with the current time and cannot backdate them,
  so the key rotation and unused credential checks pass in the demo. Their
  failing cases are covered in `tests/test_iam_checks.py` by moving the
  scanner's clock forward instead.
- moto reports the root user as having no MFA and no access keys, and there is
  no API to change that, so the root MFA check always fails here.
- moto creates buckets without default encryption. Real AWS has applied
  SSE-S3 to every new bucket since January 2023, so on a real account
  `s3-default-encryption` would normally pass.
- Resource IDs (security groups, instances, keys) are random and change every
  time the demo runs.
